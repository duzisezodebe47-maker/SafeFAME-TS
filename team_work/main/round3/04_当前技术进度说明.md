## 对老师可能认可的技术亮点

这个方向有真实工程价值：把公开文本按**预测时点之前是否可得**筛选，对语义、文本质量与数值频谱分别建模，再用置换检验决定是否启用文本候选，失败时回退同输入数值模型。数据侧给了 4 任务、两种可得性情景和来源完整性审计；模型侧给了显式 SF 交互与无文本安全退化；主控有独立验收和冻结/计分流程。这些是**设计与代码层面的亮点**。

## 老师最可能追问的缺口

1. “你们三个模块真的能跑通吗？”——目前答案是**还没有**，先修 Bundle 契约并传实际文件。
2. “创新带来多少提升？”——目前第二轮没有真实数值，必须做 Last、AR-Ridge、N、N+Q 与门控候选的同输入比较，报告负结果也可以。
3. “文本是否在当时已经公开？”——现有 `end_date` 是代理，不是核验过的发布时间；原文本也缺逐条 URL。保守滞后与 `complete_source` 零覆盖只是边界审计，不能替代真实发布时间核验。
4. “p 值与稳定性可信吗？”——必须有 999 次成功重拟合的完整逐次记录、目标不重叠半段和冻结后独立测试；目前还没有。
5. “能否由别人复现？”——需要把冻结协议、四清洗快照、正式 Bundle、模型权重、预测/置换/路由/计分哈希链交到可访问位置；现在只交了小型 Git 证据。

**下一技术里程碑：**主控收到四份清洗 CSV 并冻结 spec → 数据侧传正式 Bundle → 模型侧交 Agriculture 的校准/决策预测与 999 次 null → 主控冻结路由 → 模型侧交测试预测 → 主控独立计分。走完 Agriculture 后才有第一条新的真实技术结论，再扩另外三任务。文书和 PPT 应在这条证据链稳定后编写。
