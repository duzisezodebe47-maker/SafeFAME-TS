# 第二轮统一接口与交付节奏

**发布方：**主控电脑，分支 `team/main-eval-20260921`。**适用：**本轮跨电脑工程对接；不修改既有 v2/v3/v4 正式结果。以下是主控的**接口决策**；逐任务清洗文件哈希及正式 `split_spec` 仍待数据侧回传后冻结，禁止将尚无哈希的模板改名为正式实验。

## 1. 身份与数据口径

| 项 | 第二轮统一口径 |
|---|---|
| 电脑身份 | 数据侧＝`3218151885-creator`（现有 `辅助电脑02交付01次`）；模型侧＝`SHY`（现有 `03 辅助电脑二 交付一次`）；主控＝`team/main-eval-20260921`。名称差异不改变职责。 |
| 任务 | `Domain_hH_fF`，折号 F 为 1、2、3；例如 `Agriculture_h12_f1`。 |
| 起点 | `origin_index` 为清洗后序列 0 起算的目标起点；稳定 `origin_id` 为 `Domain:hH:fF:o<origin_index>`。预测必须同时携带两者，不能把原始行号当清洗后索引。 |
| 时间段 | `train`、`calibration`、`decision`、`test` 四段；各段半开，目标完整落在本段。模型不得自行重切。 |
| 目标尺度 | 主要评价使用数据侧训练段拟合的同一标准化目标；同时保留原始尺度目标供追溯。所有候选在同一坐标评价。 |
| 数值输入 | 本轮主比较统一使用 OT 单变量历史。Last、SeasonalNaive、AR-Ridge 也从同一 Bundle 生成；旧多变量结果只作历史参考，不进入“同输入”主比较。 |
| 特征版本 | 数据侧 `bundle_signature` 是完整输入锚点；模型侧 `config_sha256` 是模型配置锚点；两者字段不得混用。预测另记场景、代码提交和训练输入文件哈希。 |

## 2. 可得性情景与候选

- **主情景 `proxy`：**与现有 v4 的 `end_date < cutoff_time` 代理口径可比，但不等同已核验发布时间。
- **稳健性情景 `conservative_lag`：**日频固定 1 天、周频固定 7 天、月频固定 31 天；仅作预先规定的扰动，不按测试收益改值。数据侧应同时给覆盖损失与独特文本数，不能把文本数增加写成覆盖增加。
- **`complete_source`：**现有真实文本没有逐条 URL，预期覆盖 0；只输出元数据审计表，不训练和评估预测模型。
- **正式门控候选最多两条：**逐分支惩罚的 `N+S+Q`，以及在前者基础上增加**明确语义×数值频谱交互**的候选，暂名 `N+S+Q+SF`。若交互实现或置换检验未通过，第二条不进入正式门控，须在看测试结果前记录降级。现有 `N+S+Q+F` 的 F 仅是数值谱统计，可作为诊断，不得冒名为交互候选。
- **诊断消融：**`N`、`N+Q`、`N+S`、`N+F`、`N+S+Q+F`、现有 v4 两条候选和等维纯数值对照按资源选做。诊断结果不自动获得正式门控资格。`N+S` 缺文本时只令 S 贡献为零，N 仍预测；任何含 S 的候选遵守同一掩码规则。

## 3. 选择、统计与证据

1. 校准段确定数值回退、模型超参数；决策段做门控。正式两候选按既有 v4 思路：各 999 次逐行文本/质量错位，每次重拟合相关尺度、PCA 和超参数；每候选经验 `p≤0.025`，且整体决策 MSE 与两个目标不重叠半段都严格胜过数值回退。没有足够半段窗口则不放行。
2. 候选数、置换单位、随机种子、α 网格和执行代码哈希在测试计分前锁定。先用少量置换跑工程自检，**自检 p 值不用于正式门控**。测试段只在冻结路由写盘后打开一次。
3. 报 MSE、MAE、同输入数值回退相对收益、配对损失差、移动块区间、覆盖率和路由率；收益按任务折与任务族分别报告，另报去除最大收益任务族后的描述均值。任务折不能当独立数据集；历史期不能称未来确认。
4. 每次跨电脑交付都有 `manifest.json`：分支名、提交号、任务清单、完整路径、源数据/Bundle/配置 SHA256、命令、环境、耗时、通过/失败项目。输入数据未入库时给可复核的本地路径和散列值，Git 上的小型证据只能标部分覆盖。

## 4. 预先注册的工程代表任务

先跑 `Agriculture_h12_f1` 走通真实端到端；随后依次扩展 `Climate_h4_f2`（周频）、`SocialGood_h3_f1`（既有记录中训练文本为零，验证安全退化）、`Environment_h7_f2`（日频）。选取理由来自已知历史覆盖和工程边界，**不是独立新样本验证**。若某任务因数据缺口不可运行，保留失败证据，主控先登记替代任务及理由，再让模型侧运行；不得按新测试表现换任务。

## 5. 循环与分支纪律

1. **主控安排（第 0–2 天）：**发布接口决策与代表任务清单，收到数据侧清洗快照 SHA256 后填入正式 `split_spec`，冻结候选、种子、规则及主控自身代码版本。
2. **数据侧交付（建议第 3–6 天）：**在 `3218151885-creator` 分支新增第二次交付目录，先交 4 个任务的 `proxy`/`conservative_lag` Bundle 与接口测试；不触碰主控或模型分支。
3. **模型侧交付（数据冻结后约 4–6 天）：**在 `SHY` 分支新增第二次交付目录，直接读上述 Bundle，先 1 项真实任务再补代表任务；不触碰其他分支。
4. **主控验收（模型交付后约 2 天）：**独立重算、登记失败/修正、发布下一轮三份任务。每一轮都是“主控安排 → 分支交付 → 主控验收”，未通过项回到原负责人分支修复。
5. **统一主目录：**三方第二轮验收通过后再提交有来源和哈希清单的整合提案；合并 `main` 是单独步骤，不能把个人分支直接当最终统一版本。
